# Frontend Rules (React + Vite + TypeScript)

Feature-folder architecture. Every feature is generated by `npm run gen <feature-name>`
and is self-contained. No feature reaches into another feature's internals.

## Project docs

Read these before building a feature — this file is architecture/conventions only, not
business rules or schema:
- `../docs/project-overview.md` — product scope, domain rules (transaction types, credit
  card model, budgets), functional requirements.
- `../docs/data-model.md` — backend entities/columns/relationships. Types in `types/` and
  Zod schemas should mirror this shape, not invent a different one.

## Folder structure (strict)

```
frontend/
  scripts/
    generate-feature.js       -> npm run gen <feature-name>

  src/
    api/
      axiosClient.ts           -> single axios instance, base URL, interceptors
      queryClient.ts           -> react-query QueryClient config (staleTime, retry, etc.)

    ui/                        -> shadcn/ui primitives ONLY (button.tsx, dialog.tsx, input.tsx...)
                                   generated via `npx shadcn add <component>`. No business
                                   logic here, ever. Styling/token tweaks are fine.

    components/                -> shared, generic, cross-feature components built on top of
      layout/                     ui/ primitives (AppShell, PageHeader, DataTable, FormField
      feedback/                   wrapper, ConfirmDialog). If a component references a
                                   feature concept (e.g. "Order"), it does NOT belong here.

    hooks/                     -> shared, cross-feature hooks only (useDebounce, useMediaQuery)
    store/                     -> zustand stores — global/client state ONLY, one file per
                                   concern (authStore.ts, uiStore.ts). Server data never
                                   lives here — that is react-query's job.

    schemas/                   -> global zod schemas reused across features
                                   (pagination.schema.ts, apiResponse.schema.ts)
    types/                     -> global types mirroring backend contracts
      apiResponse.types.ts      -> ApiResponse<T>, matches backend ApiResponse<T> exactly
      pagination.types.ts       -> PageRequest<TFilter>, PageSorting, PagedResult<T>
      errorStatus.enum.ts       -> mirrors backend ErrorStatus enum values exactly

    constants/                 -> app.constants.ts, routes.constants.ts

    routes/                    -> route definitions, react-router setup
      AppRouter.tsx

    features/
      <feature-name>/           -> generated by `npm run gen <feature-name>`
        api/                     -> raw axios call functions only, e.g. getProducts(),
                                     createProduct(payload). Return unwrapped typed data.
                                     No react-query here, no components importing this
                                     directly except through hooks/.
        components/              -> feature-specific components (ProductForm, ProductRow)
        hooks/
          queries/                -> useProducts.ts, useProduct.ts (useQuery wrappers)
          mutations/               -> useCreateProduct.ts, useUpdateProduct.ts (useMutation wrappers)
        schemas/                 -> zod schemas (createProductSchema, productFilterSchema)
        types/                   -> types for this feature; prefer `z.infer<typeof schema>`
                                     over hand-written duplicate interfaces where a schema exists
        pages/                   -> route-level components (ProductsPage, ProductDetailPage)
        constants/               -> feature-local constants
        index.ts                 -> barrel: exports ONLY what other features/routes are
                                     allowed to use (pages, and rarely a component/hook).
                                     Everything else is private to the feature.

  App.tsx
  main.tsx
```

## Feature generator

```bash
npm run gen product-catalog
```

runs `scripts/generate-feature.js`, which scaffolds the folder set above under
`src/features/<name>/` and a blank `index.ts`. Always generate a feature this way —
never hand-create a folder under `src/features/` with a different shape.

## Rules

1. **`ui/` is shadcn territory.** Only touch it to add/update primitives via the shadcn
   CLI or adjust design tokens (colors, radius, spacing) in existing primitives. Never
   put feature or business logic inside `ui/`.
2. **`components/` is generic only.** If you're unsure whether something is "common" or
   feature-specific, ask: does it reference a domain concept (Product, Order, User)? If
   yes, it belongs in `features/<name>/components/`.
3. **Data flow is one-directional and layered:**
   `api/*.ts` (axios call) → `hooks/queries|mutations/*.ts` (react-query wrapper) →
   `components/` or `pages/` (consumes the hook).
   Components and pages **never** call axios or `api/` functions directly.
4. **Zod is the source of truth for shape + validation.** Define a schema in `schemas/`,
   derive the TypeScript type with `z.infer<typeof schema>` in `types/`, and use the same
   schema with `zodResolver` in `react-hook-form`. Don't hand-write a parallel interface
   that duplicates a schema that already exists.
5. **react-hook-form for all forms.** No manually-managed form state via `useState` for
   anything with more than one field.
6. **react-query owns all server state.** No server data (lists, entities, API results)
   is ever stored in zustand or component state — always `useQuery`/`useMutation`, with
   feature hooks in `hooks/queries` / `hooks/mutations`. On mutation success, invalidate
   the relevant query key rather than manually patching cached data unless there's a clear
   optimistic-update need.
7. **zustand is for client-only global state**: auth session, theme, sidebar open/closed,
   multi-step wizard state that must survive navigation. If it comes from the API, it's
   not a zustand candidate.
8. **Types mirror backend DTOs/enums exactly** — `types/errorStatus.enum.ts` matches the
   backend `ErrorStatus` enum values, `ApiResponse<T>` and `PagedResult<T>` mirror the
   backend shapes. When a backend DTO changes, update the matching type — don't invent a
   different shape on the frontend.
9. **Query keys are centralized per feature** — export a `productKeys` object (or similar)
   from `hooks/queries/` so keys aren't duplicated as ad-hoc arrays/strings across files.
10. **Feature encapsulation**: other features/routes may only import from a feature's
    `index.ts` (`import { ProductsPage } from "@/features/products"`), never deep-import
    (`@/features/products/hooks/queries/useProducts` from outside the feature).
11. **Route-level components live in `pages/`**, are registered in `routes/AppRouter.tsx`,
    and compose feature components — they are not where business/data logic lives.
12. Before creating a new component/hook, check if a similar one exists in another feature
    and mirror its structure exactly.

## API response & error handling

- `axiosClient.ts` has a response interceptor that unwraps the backend's `ApiResponse<T>`
  envelope and normalizes errors using `ErrorStatus` (map to toast messages / redirect to
  login on `UnAuthorized`/`TokenExpired`, etc.) — this logic lives in **one place**, not
  repeated in every `api/*.ts` function or every component's `catch` block.
- List/dashboard endpoints use `PageRequest<TFilter>` as the request payload and expect
  `PagedResult<T>` back, matching the backend exactly:

```ts
// types/pagination.types.ts
export interface PageSorting {
  field?: string;
  direction?: "asc" | "desc";
}
export interface PageRequest<TFilter> {
  page: number;
  pageSize: number;
  sorting?: PageSorting;
  filters?: TFilter;
}
export interface PagedResult<T> {
  items: T[];
  totalCount: number;
  page: number;
  pageSize: number;
}
```

```ts
// features/products/hooks/queries/useProducts.ts
export const productKeys = {
  all: ["products"] as const,
  search: (req: PageRequest<ProductFilterRequest>) =>
    [...productKeys.all, "search", req] as const,
};

export function useProducts(req: PageRequest<ProductFilterRequest>) {
  return useQuery({
    queryKey: productKeys.search(req),
    queryFn: () => searchProducts(req), // api/products.api.ts
  });
}
```

## Anti-patterns to actively avoid

- Fetching in `useEffect` + `useState` instead of react-query.
- Calling `axios`/`api/*.ts` functions directly from a component or page.
- Duplicating a zod schema as a separately hand-written TS interface.
- Putting server data (API results) into a zustand store.
- Editing `ui/` primitives to add feature-specific behavior instead of composing in
  `components/` or `features/<name>/components/`.
- Deep-importing another feature's internals instead of going through its `index.ts`.
- Ad-hoc query key strings/arrays repeated across files instead of a centralized key factory.
- Prop-drilling data through 4+ component levels instead of a feature hook/context.

## New feature checklist

1. `npm run gen <feature-name>`
2. `schemas/` — zod schema(s) for request/response shapes and filters.
3. `types/` — `z.infer` types + anything not covered by a schema (mirrors backend DTO).
4. `api/` — axios functions calling the backend endpoints, typed with the above.
5. `hooks/queries` / `hooks/mutations` — react-query wrappers + centralized query keys.
6. `components/` — feature UI, built from `ui/` primitives and shared `components/`.
7. `pages/` — route-level composition.
8. `index.ts` — export only the pages (and any component/hook meant for reuse elsewhere).
9. Register the page(s) in `routes/AppRouter.tsx`.

## Naming

- Components: PascalCase, file name matches export (`ProductForm.tsx`).
- Hooks: camelCase, prefixed `use` (`useProducts.ts`, `useCreateProduct.ts`).
- Schemas: camelCase, suffixed `Schema` (`createProductSchema`).
- Types/interfaces: PascalCase (`ProductDto`, `CreateProductRequest`).
- API functions: verbNoun (`getProducts`, `createProduct`, `updateProduct`, `deleteProduct`).

## Stack

- React 18 + Vite + TypeScript

- react-hook-form + zod (`@hookform/resolvers/zod`)
